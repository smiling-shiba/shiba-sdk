# Pack Format: Policy, Templates, Assets

Status: Proposal. Names and fields are illustrative and can change. Terms follow decision D-34.

**Scope note:** every example is a neutral **toy domain** ("entities" and "collections") that exists only to test the toolset. No game content is defined here. A real game is built later, in its own repo, after the toolset is stable.

## Goal

Build a **shell/framework** into which someone drops custom rules and plays a game:

- **Policy:** the rules as code (JS/TS), built to one bundle and signed.
- **Templates:** YAML files describing objects. Data, not code. They may call policy functions by name with arguments.
- **Assets:** art, audio and other files that templates reference.
- **Pack:** a policy plus its templates and assets.

`sht` (`shiba-tools`) builds and signs policies, validates templates against the policy's contract, and packs them. `shiba-app` loads a pack. The ladder server (`shiba-mps`) does not: it runs its own rules (D-42).

## 1. Who owns what

| Repo | Role |
|---|---|
| `shiba-sdk` | SDK: `definePolicy(...)` and friends for writing a policy, and contract generation. Ships a toy policy as its example and test fixture. Does not run policies. |
| `shiba-tools` (`sht`) | Build, validate, pack, sign, verify. |
| `shiba-app` | Shell. Ships with empty `policies/`, `templates/` and `assets/`. Loads a pack. |
| `shiba-mps` | Official server. Runs its own rules in Elixir; does not load a policy (D-42). |
| Game data repo (later) | Policy source, templates, assets, for one game. Separate repo, own visibility. |

## 2. Pack layout

What `shiba-app` loads (and what a game repo produces):

```text
<pack>/
  pack.yml                 # pack metadata; names the active policy
  policies/
    toy-policy-2026.09.19.1.js             # built, minified policy bundle
    toy-policy-2026.09.19.1.contract.json  # generated: kinds, functions, hooks (with JSON Schemas)
    toy-policy-2026.09.19.1.sig.json       # signature (optional in local mode)
  templates/
    entities/crate.yml
    collections/starter-set.yml
  assets/
    ...
```

Policy files are named `<id>-policy-<calver>` plus an extension. The calver is `YYYY.MM.DD.N` (date plus a build number) and is generated by `sht build-policy`. Several versions may sit side by side for easy rollback, but a pack names exactly **one** active policy in `pack.yml`.

`shiba-app` ships these three folders empty (`policies/`, `templates/`, `assets/`). It should also accept a configurable **pack directory**, so game data can live outside the public repo. Default: the empty folders in the app's data directory.

`pack.yml`:

```yaml
id: toy-pack
version: 2026.09.19.1          # generated calver
policy: toy-policy-2026.09.19.1   # the one active policy, found in policies/
sdk:
  range: ">=0.1.0 <0.2.0"      # SDK versions this pack targets (semver)
templates: templates/**/*.yml
assets: assets/
```

## 3. Writing a policy (game repo, with the SDK)

The SDK lives in `shiba-sdk` (guide: [sdk.md](sdk.md)); the package name is not final. Example, using the toy domain:

```ts
// src/index.ts in the game repo
import { definePolicy, fn, hook, kind, t } from 'shiba-sdk'

export default definePolicy({
  id: 'toy',                    // the version is generated by `sht build-policy`, not written here

  kinds: {
    entity:     kind({ name: t.string({ minLength: 1 }), tags: t.optional(t.array(t.string())) }),
    collection: kind({ entities: t.array(t.ref('entity')) }),
  },

  hooks: {
    created: hook({ title: 'Created' }),
    updated: hook({ title: 'Updated' }),
  },

  functions: {
    set_value: fn({
      title: 'Set value',
      args: { key: t.string({ minLength: 1 }), value: t.integer({ minimum: 0 }) },
      run(ctx, { key, value }) { /* deterministic; typed arguments */ },
    }),
  },
})
```

`sht build-policy` type-checks (if TS), validates registrations, forbids host imports, bundles to `policies/<id>-policy-<calver>.js`, and generates the matching `.contract.json` from the definitions. The calver is generated, not typed by hand.

Policy functions follow the determinism rules in `engine-api.md`: pure, injected RNG, no clock, network or filesystem.

## 4. Writing templates (YAML)

The flexible approach: a template may **call policy functions by name with arguments**. It never contains code.

```yaml
# yaml-language-server: $schema=../.shiba/entity.schema.json
kind: entity
id: crate
name: Crate
tags: [container]

on: created                     # a hook declared by the policy
do:
  - fn: set_value               # a function declared by the policy
    args:
      key: weight
      value: 5
  - fn: add_tag
    args:
      tag: heavy
```

```yaml
kind: collection
id: starter-set
entities: [crate, lamp]         # references; each must resolve
```

Explicit `fn` and `args` keys (no single-key shorthand) keep schemas, error locations and autocomplete simple. A shorthand can come later.

**Not in v1:** conditions and expressions, computed values, scripting in YAML.

## 5. The contract (`policies/<name>.contract.json`)

Generated from the policy. `sht` and editors read this; they never read or run the policy bundle.

```json
{
  "policy": { "id": "toy", "version": "2026.09.19.1", "sha256": "…" },
  "sdk": { "version": "0.1.0" },
  "kinds": {
    "entity": {
      "schema": {
        "type": "object",
        "required": ["name"],
        "properties": { "name": { "type": "string", "minLength": 1 },
                        "tags": { "type": "array", "items": { "type": "string" } } }
      }
    }
  },
  "hooks":     { "created": { "title": "Created" }, "updated": { "title": "Updated" } },
  "functions": {
    "set_value": {
      "title": "Set value",
      "args": {
        "type": "object", "required": ["key", "value"], "additionalProperties": false,
        "properties": { "key": { "type": "string", "minLength": 1 },
                        "value": { "type": "integer", "minimum": 0 } }
      }
    }
  }
}
```

Only functions, hooks and kinds explicitly registered appear here. Anything else does not exist as far as templates are concerned.

Conventions (implemented in `sht validate`, see `shiba-tools/docs/validation.md`):

- `kind`, `id`, `on` and `do` are framework fields, valid on every template and not listed in a kind's schema. Any other key that is not in the kind's schema is rejected.
- A reference field is marked in the kind's schema with the custom keyword `"x-shiba-ref": "<kind>"`, on a string or on the items of an array of strings.

## 6. Validation (`sht validate`)

Runs in order and reports every diagnostic it can:

| # | Layer | Checks |
|---|---|---|
| 1 | YAML syntax | Parses as YAML 1.2. |
| 2 | Kind and shape | `kind` is declared by the policy; the file's fields match that kind's schema. |
| 3 | References | `ref` fields (like `entities`) resolve; ids are unique; asset paths exist. |
| 4 | Contract | `fn` and `on` exist in the contract; `args` match that function's schema. |
| 5 | Compatibility | `pack.yml` `sdk.range` is satisfied by the policy's SDK version. |
| 6 | Semantics (later) | Cross-file checks. |

Diagnostic shape: severity, file, line, column, code, message, suggestion, related symbol.

Examples from a deliberately broken toy file:

```text
templates/entities/crate.yml:9:9    error  SH101  Unknown function "set_valeu". Did you mean "set_value"?
templates/entities/crate.yml:11:14  error  SH204  Argument "value" must be an integer >= 0 (got "heavy")
templates/collections/starter-set.yml:2:22  error  SH301  Unknown entity "lamp2". Did you mean "lamp"?
pack.yml:3:10                       error  SH501  SDK 0.3.0 does not satisfy ">=0.1.0 <0.2.0"
```

(Code prefixes are placeholders.)

## 7. Build, sign, verify

| Command | Does |
|---|---|
| `sht build-policy` | Policy source to `policies/<name>.js` + `.contract.json`, with a SHA-256 and a generated calver. |
| `sht validate` | Templates (and assets) against the active policy's contract. |
| `sht pack` | Checks the pack, then writes `pack.lock.json`: every file with its hash. YAML and JSON files are hashed in canonical form (RFC 8785), so comments and formatting do not matter. |
| `sht keygen` | Makes an ed25519 key pair (`.key` private, `.pub` public). |
| `sht sign` | Signs the canonical lock with a private key, writing `pack.sig.json`. |
| `sht verify` | Checks the files against the lock, and the signature against trusted public keys (`--trust`). |

One signature covers the whole pack (policy, templates, assets and `pack.yml`), for local and official use alike, because template values also affect outcomes. Details: `shiba-tools/docs/signing.md`. The server should still use its own copies for official play.

- Local development uses a throwaway dev key. The real key lives in CI only.
- Local/custom mode may run an unsigned policy with a visible warning. Signed policies are verified against a trusted key.
- Signing gives provenance and integrity, not secrecy.

## 8. How `shiba-app` loads a pack

```text
pick pack dir -> find the active policy named in pack.yml -> verify its signature (or warn if unsigned, local mode)
  -> load the policy bundle -> read the contract
  -> validate templates against the contract -> run
```

## 9. VS Code (no GUI needed)

`sht schemas` generates `.shiba/template.schema.json` (one schema for all templates, switching on `kind`) and `.shiba/pack.schema.json` from the contract, plus a `.vscode/settings.json` mapping. With the Red Hat YAML extension, VS Code then autocompletes `kind`, `on`, `fn` and `args`, offers snippets for whole steps and templates, suggests existing ids for reference fields, shows hover text, and flags shape errors as you type. Contract and cross-file errors (duplicate ids) still need `sht validate`. Setup and things to try: `shiba-tools/docs/vscode.md`.

## 10. Decisions and open items

Decided 2026-09-20:

1. **Versioning:** generated calver `YYYY.MM.DD.N` for policies and packs. The SDK (`shiba-sdk`) keeps ordinary semver.
2. **Unknown fields:** rejected (a typo is an error).
3. **One policy per pack.** Several versions may sit in `policies/`; `pack.yml` names the active one.
4. **Policies are found by name** in `policies/`; no database or separate ID registry.
5. **Assets are referenced by relative path** (for example `assets/cards/fish.png`). IDs can come later if it gets annoying.
6. **One generated contract file** per policy, not two.
7. **Hot reload** (a watch mode) is wanted, later.
8. **Schema library:** describe kinds and arguments with TypeBox, which `shiba-tools` already depends on. Adopted unless a problem appears.

Leaning, not final:

9. **Trusted keys:** `shiba-app` keeps a folder of public-key files; the official key ships in it; additional keys can be added. Signed policies verify against them. Unsigned policies run in local mode with a visible warning. The official ladder accepts only the official key.

Still open:

10. Signature file naming and format details (key id, algorithm agility).
11. Exact set of fields in `pack.yml`.

## 11. First slice (proposed)

1. Hand-write a `contract.json` for the toy policy as a fixture in `shiba-tools`.
2. Write the sample templates plus one deliberately broken one.
3. Build the validator until the broken file produces the diagnostics above.
4. Build the toy policy in `shiba-sdk` (with the SDK's `definePolicy`) that emits the same contract; swap the fixture.
5. `sht build-policy`, `sht pack`, `sht sign` with a dev key, `sht verify`.
6. `shiba-app` loader that verifies and loads the toy pack from empty default folders.

The toy policy and templates stay as permanent test fixtures.
